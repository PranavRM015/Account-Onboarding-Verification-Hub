# Review service: Intake integration and ticket review

Review owns `Tickets`, `Flags`, `VendorResponses`, `Decisions`, and `AuditTrails` in its own SQL Server database. It preserves the monolith's review endpoints, row locks, row-version concurrency, two-reviewer High-risk approvals, and 60-day expiration. It never writes Intake profiles or Identity credentials, and has no database foreign keys to those services.

## Start locally

From the repository root, with .NET 10, dotnet-ef 10, SQL Server, and Identity running:

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet ef database update --project services/review/Review.Api.csproj
dotnet run --project services/review/Review.Api.csproj --launch-profile http
```

Development uses Windows authentication to `localhost`, database `VerificationHub_Review`, and listens at `http://127.0.0.1:5292`. The initial migration creates only Review's tables and installs `dbo.pr_expireReviewTickets`. It does not change or copy the monolith, Intake, or Identity databases. Point Review at a new, empty database; do not run its baseline against an existing monolith/Intake database.

For historical tickets, `database/MigrateFromMonolith.sql` is a separate, optional one-time copy after applying Review's baseline. Stop ticket writers and the expiry workers during a coordinated cutover; back up both databases first. Run it with SQLCMD variables `SourceDatabase` and `ReviewDatabase`, for example:

```powershell
sqlcmd -S localhost -E -C -b -v SourceDatabase="YourMonolithDatabase" ReviewDatabase="VerificationHub_Review" -i services/review/database/MigrateFromMonolith.sql
```

The copy reads the old backend schema, preserves ticket/flag/decision/audit IDs and dates, creates customer display snapshots, and writes no profiles, credentials, or source tables. The target must be empty; a repeat run against a populated target fails instead of duplicating records. Verify counts and sample ticket details before routing users to Review. Do not use it as ongoing synchronization or to copy Intake's partially initialized ticket read-model table.

| Setting / environment variable | Meaning |
|---|---|
| `ConnectionStrings:ReviewConnection` / `ConnectionStrings__ReviewConnection` | Required Review SQL connection string; development default is in `appsettings.Development.json`. No production default. |
| `Identity:JwksUrl` / `Identity__JwksUrl` | Full JWKS address. Development: `http://localhost:5290/.well-known/jwks.json`. Required in production. |
| `Identity:Issuer`, `Identity:Audience` | Both default to `AccountVerificationOnboardingHub`; match Identity. |
| `Identity:RequireHttps` | `true` by default; `false` for local Development. Explicitly set `false` only for HTTP on the team's private service network. |
| `Database:MigrateOnStartup` | Defaults to `false`. Set `true` to apply Review's migrations on startup (including in the Compose overlay). |
| `TicketExpiry:Enabled` | Defaults to `true`. Runs expiration once at startup and periodically. |
| `TicketExpiry:IntervalMinutes` | Defaults to `60`. |
| `ASPNETCORE_URLS` | Configurable listener when not using the local launch profile. Container: `http://+:8080`. |

`GET /health` is a public process check; `GET /health/ready` checks access to the ticket table and returns `503` if unavailable. Neither endpoint validates Identity availability. Both return `200` with `{ "status": "ok" }` when healthy.

## Authentication

Every ticket endpoint, including `/internal/**`, requires the forwarded admin token:

```text
Authorization: Bearer <Identity admin JWT>
Content-Type: application/json
```

JWTs must use RS256 and the lowercase `admin` role. Review uses Identity's public JWKS, validates issuer, audience, signature and expiry with 30 seconds of grace, and reads `name` and `adminId` claims. Ticket creation requires a positive `adminId` and nonempty `name`; assignment and flag attribution come from the token, not the body. No Identity private key, credentials database, cookie, or `X-Internal-Key` is used. As with Risk, revoked tokens are not checked against Identity's database and may work until expiry. Keep internal routes off the public gateway.

## For Intake: create a ticket

`POST /internal/tickets`

Submit a saved customer ID, profile snapshot, account information, and Risk's assessment. Flatten Risk's `riskRating`, `flags`, and `vendorResponse` into the body below without changing their fields. `requestId` is a new GUID generated by Intake for the logical submission; retain it and reuse it on retries. Do not generate a different request ID after a timeout.

```json
{
  "requestId": "7f9de745-b972-4579-abbe-e7d92cdc4218",
  "customerId": 42,
  "accountType": "Individual",
  "jointCustomerId": null,
  "jointCustomerName": null,
  "customer": {
    "firstName": "Sam",
    "middleName": "Lee",
    "lastName": "Taylor",
    "dateOfBirth": "1985-04-12",
    "gender": "Other",
    "taxIdType": "SSN",
    "residentialAddress": "12 Main Street",
    "countryOfResidence": "US",
    "countryOfCitizenship": "US",
    "occupation": "Teacher",
    "employer": "City School"
  },
  "riskRating": "Low",
  "flags": [],
  "vendorResponse": {
    "nameMatch": "Match",
    "dateOfBirthMatch": "Match",
    "addressMatch": "Match",
    "taxIdMatch": "Match",
    "score": 50,
    "riskCodes": ""
  }
}
```

- `customerId` must be positive and may have only one ticket. Review trusts Intake to verify the profile exists. It stores an immutable display snapshot; it does not call Intake or read its database.
- `accountType` is `Individual` or `Joint`. Joint requires a positive, different `jointCustomerId` and nonempty `jointCustomerName` (max 151 characters). Intake verifies the second profile exists. Individual requires both joint fields to be null/omitted.
- Snapshot names are required (max 50 each); middle name is optional. Birth date must be on/after 1900-01-01 and describe an adult. Gender is `Male`, `Female`, or `Other`; tax ID type is `SSN`, `ITIN`, or `EIN`. Address is required (max 200); residence/citizenship are uppercase two-letter codes; occupation/employer are required (max 100).
- Do not send passwords, recovery answers, full tax IDs, or tax ID hashes. The snapshot contains none of them.
- `flags` is an array of unique violation strings: `VerificationFailed`, `OfacMatch`, `ClosedJurisdiction`, `ProhibitedIndustry` (max four). `riskRating` must agree: High for OFAC/industry, Medium for other flags, Low for none. `VerificationFailed` must agree with a reduced vendor score or nonempty risk codes.
- Vendor match fields are `Match`, `Partial`, or `NoMatch`; score is 0–50; `riskCodes` is a comma-separated string (max 200), including `""` for none. This is the existing Risk contract, not saved database objects.

On success (`200`):

```json
{
  "message": "Customer saved",
  "customerId": 42,
  "ticketId": 1,
  "riskRating": "Low",
  "verified": true,
  "flags": [],
  "vendorResponse": { "score": 50, "riskCodes": "" }
}
```

The legacy success message is preserved for the Angular flow; Review has saved a ticket, not the customer's profile or login. A successful response means the ticket, vendor row, flags, and two initial audit rows committed in one transaction. The ticket starts in `Review`; its deadline is creation plus 60 days. `verified` means no flags were raised, matching the original API.

### Retry and duplicate handling

The same `requestId`, same bound payload, and same admin produce `200` with the original ticket, without another insert. Reusing a request ID for different content/caller returns `409`. A different submission for an already-ticketed customer returns `409`. Unique indexes on both request ID and customer ID protect concurrent submissions even when Intake's customer lock is not yet implemented. This does not replace Intake's own claim/lock around its profile and login operations.

`GET /internal/tickets/by-customer/{customerId}` returns the same success shape, or `404` if no ticket exists. Intake can use it to reconcile submission state after a lost response, and to replace its direct reads of the old `Tickets` table. It requires an admin JWT. Review's database is separate: Intake's current `TicketReadModel` will not automatically see these tickets.

Use a bounded HTTP timeout and forward the admin JWT unchanged. On a timeout, a ticket might already have committed: retry with the same request ID before compensating or deleting a profile. Analysis is done by Risk first; Review does not call Risk again. Stable submission identifiers and customer state/claim handling belong to Intake.

### Filter Intake's pending customer list

`GET /internal/tickets/onboarded-customer-ids` requires the same forwarded admin Bearer token. It returns `200` with a plain array of distinct primary customer IDs, sorted ascending:

```json
[17, 42, 58]
```

All existing ticket statuses are included, including Submitted, Review, Approved, and Rejected. This means "has a ticket," not "has been approved." Joint holder IDs are not added unless they also have their own ticket. With no tickets it returns `[]`. Intake should exclude these IDs from its pending list. Authentication errors are `401`/`403`; database/query failures return `500` problem details and must not be treated as an empty list. This lookup is for display filtering; the ticket-creation uniqueness checks still protect against concurrent submissions after the list was loaded.

## For the review UI

These preserve the existing Angular URL paths and response field names:

| Endpoint | Behavior |
|---|---|
| `GET /api/admins/tickets` | Review queue ordered by verification deadline; entries have `ticketId`, `customerName`, `riskRating`, `verificationDeadline`. |
| `GET /api/admins/tickets/{ticketId}` | Full ticket, saved customer snapshot, flags, vendor response and final decision. Missing ticket: `404`. |
| `POST /api/admins/tickets/{ticketId}/flags/{flagId}/clear` | Body `{ "reason": "Reviewed documents" }`; records the caller's admin ID/name and an audit row. |
| `POST /api/admins/tickets/{ticketId}/approve` | Body `{ "reason": "All checks passed" }`; all flags must be cleared. High risk needs approvals from two different usernames; first approval returns `200` while remaining in Review. |
| `POST /api/admins/tickets/{ticketId}/reject` | Body `{ "reason": "Could not verify" }`; flags may remain uncleared. |

Reasons are required, trimmed, and at most 500 characters. Mutations acquire `UPDLOCK, ROWLOCK, NOWAIT` on the ticket inside the same transaction as their changes, then recheck ticket state. A competing writer gets `409` promptly. Row-version concurrency is also enabled. Final decisions cannot be overwritten; decisions and audit records cannot be edited/deleted through EF. Late approval/clearing/rejection requests receive `409` once the deadline has passed; expiration records a system rejection instead.

`pr_expireReviewTickets` atomically changes overdue Review tickets to Rejected and writes their decision/audit rows. It skips currently locked rows, which the next run picks up, and does not insert duplicate decisions on repeat runs. No synthetic Identity admin is needed for the `system` attribution.

## Errors

| Code | Meaning |
|---|---|
| `400` | Invalid JSON/body/fields; validation problem details or an explanatory string. Correct the request. |
| `401` | Missing/invalid/expired token, or missing identity claims needed for the operation. |
| `403` | Valid token without the lowercase admin role. |
| `404` | Requested ticket/flag/customer ticket not found. |
| `409` | Duplicate/conflicting submission, ticket busy/stale, invalid ticket state, uncleared flag, late action, or second High-risk approval by the first reviewer. |
| `415` | Body content type is not supported; send JSON. |
| `503` | No cached Identity keys and key retrieval failed; readiness also returns this if the DB is unavailable. |
| `500` | Unexpected failure or unavailable database during an operation; generic problem response. No success should be inferred. |

Network timeouts have no HTTP status. On any non-success, Intake must not fabricate a ticket ID or mark a customer onboarded. A High risk rating is not an HTTP error.

## Docker

```powershell
docker build -t verificationhub-review -f services/review/Dockerfile services/review
docker compose -f docker-compose.yml -f services/review/compose.review.yml up --build
```

The overlay adds Review to the team's existing SQL/Identity network without modifying their Compose file. It needs the same root `.env` values. Inside that network Review listens at `http://review:8080`; on the host it is `http://127.0.0.1:5292`. Intake must use the container name rather than its own localhost. The image runs as the runtime image's non-root app user. Docker build/run must be verified on a machine with Docker installed.

## Intake handoff: work deliberately not done here

No Intake or Identity source/configuration was modified. Their submission endpoints still return `501` until the Intake owner connects them:

1. Keep customer profile creation, Identity account creation, customer locks/claims and compensation in Intake. Review never saves credentials or writes those services' tables.
2. Call Risk and forward the result plus the saved profile snapshot to `POST /internal/tickets`. Return Review's result to Angular on success.
3. Replace Intake's direct shared-database ticket queries with Review lookups or coordinated Intake onboarding status. Review uses a separate database.
4. Resolve the admin-created customer ordering with the team: Review requires a real allocated customer ID, while profile/login writes and Review's transaction are separate operations. They cannot be made one SQL transaction across these services by this API. Use a durable pending submission/claim and reconciliation/compensation; do not blindly delete profiles after an ambiguous timeout. The current Identity contract has account creation but no account-deletion compensation endpoint.
5. Route `/api/admins/tickets/**` to Review and leave `/internal/**` private. Existing frontend URLs stay the same.

This delivers the Review side of the boundary, not a claim that the unmodified Intake's two incomplete endpoints now work end-to-end.
